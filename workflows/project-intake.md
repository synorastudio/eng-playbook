# Project intake workflow

Use Project Intake when project context begins in an External Project Brief rather than in accepted repository truth.

## Entry

Gather the supplied notes, documents, links, user flows, sketches, research, and existing project artifacts. Record source provenance when it will help future readers find or reassess the upstream context.

## Flow

1. Extract the desired outcome, users, feature candidates, constraints, existing decisions, non-goals, open questions, risky assumptions, and vocabulary candidates.
2. Keep source claims separate from decisions already accepted in the project. Surface conflicts instead of silently resolving them.
3. Separate current scope from backlog and speculative ideas. Presence in the brief does not make an idea accepted work.
4. Produce a concise intake summary that omits empty sections and preserves material uncertainty.
5. Choose the next Workflow from the state of the work: Project Adoption, Feature Planning, documentation maintenance, or direct Implementation of an already accepted slice.

## Completion

Intake is complete when every material source claim is represented or deliberately excluded, conflicts remain visible, and current scope is distinguishable from later possibilities. Intake does not authorize production implementation or create project facts by itself.

The portable `intake` Skill provides a procedure for carrying out this Workflow.
